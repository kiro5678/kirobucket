## Runtime behaviour checks

### Orfeo 1.7.3 — Scoop-managed Setup payload extraction

- The official Windows Portable asset (`Orfeo-1.7.3-portable.exe`) is an NSIS self-extracting launcher, not a complete app archive. 7-Zip can extract its outer container, but it exposes only four bootstrap files and does not produce the required `Orfeo.exe` plus `resources/app.asar` application tree. When launched normally, it extracts and runs the application from `%TEMP%`.
- The official Setup asset (`Orfeo-Setup-1.7.3.exe`) contains the complete application in `$PLUGINSDIR/app-64.7z`. The manifest now downloads this Setup container as `#/dl.7z`; Scoop extracts the outer NSIS layer into its version directory, then `pre_install` expands the nested 7z payload into the same directory before Scoop creates shims and shortcuts.
- The manifest verifies `Orfeo.exe`, `resources/app.asar`, `resources/native/orfeo_audio.node`, and `resources/native/orfeo-review.exe`. It creates `Orfeo.cmd`, which sets `PORTABLE_EXECUTABLE_DIR` to the app directory so Orfeo stores `Orfeo-Data` in Scoop's persisted data location. The transient `$PLUGINSDIR` and uninstaller files are removed after extraction.
- Windows GitHub Actions run [44442604728](https://github.com/kiro5678/kirobucket/actions/runs/44442604728) passed the manifest's actual `pre_install` script after reproducing Scoop's outer extraction order. It verified the Setup SHA-256 (`4219b3e689ac5bb29949c1f378f665082f7379ab0ebe56a24bed94c506848728`), all required app files, and direct execution of four `Orfeo.exe` processes from the Scoop version directory rather than TEMP. The test observed 56 files in the persisted `Orfeo-Data` directory after launch.
- The separate Portable diagnostic [run 44318206990](https://github.com/kiro5678/kirobucket/actions/runs/44318206990) confirmed runtime extraction under TEMP. The diagnostic workflow was later decoupled from the Scoop manifest and its current upstream-asset check passed in [run 44443082506](https://github.com/kiro5678/kirobucket/actions/runs/44443082506).
- A full real-Scoop lifecycle test [run 44448560834](https://github.com/kiro5678/kirobucket/actions/runs/44448560834) passed on Windows with PowerShell 7. It ran `scoop install orfeo`, launched through Scoop's generated `orfeo.cmd` shim, verified the Start Menu shortcut and the actual `Orfeo-Data` Junction into `persist`, then ran `scoop uninstall orfeo`. The app folder, shim, and shortcut were removed while a marker file in `Orfeo-Data` survived. The workflow reinstalled Orfeo, verified the same marker through the new Junction, launched again, and completed a second uninstall while retaining the marker.
- During both launches, four `Orfeo.exe` processes were observed executing from `apps\\orfeo\\current`, not the isolated TEMP directory. Orfeo created 56 persisted files after the first launch and 58 after the second.
- Scope: this was a real Scoop CLI lifecycle on a disposable Windows GitHub Actions runner using PowerShell 7, not on the user's physical machine. It verifies install, shim/shortcut creation, launch path, uninstall, reinstallation, and persisted-data retention. It does not exhaustively test interactive GUI features or every application function.
- Evidence: [manifest](../bucket/orfeo.json), [Scoop extraction workflow](../.github/workflows/orfeo-scoop-extraction-experiments.yml), [full Scoop lifecycle workflow](../.github/workflows/orfeo-scoop-lifecycle-test.yml), and [Portable TEMP diagnostic](../.github/workflows/orfeo-portable-temp-test.yml).
- Evidence: [manifest](../bucket/orfeo.json), [Scoop extraction workflow](../.github/workflows/orfeo-scoop-extraction-experiments.yml), and [Portable TEMP diagnostic](../.github/workflows/orfeo-portable-temp-test.yml).

### NixanDeck 1.0.0-beta.1 — Scoop MSIX payload extraction (2026-11-20)

- The official Windows 11 x64 ZIP (82,115,714 bytes; SHA-256 `97c275417e4ee3355241ee015a5dde4753358b44f9f4e4b15bf101bb31fe5af8`) wraps `NixanDeck.msix`, `NixanDeck.cer`, and `Install.bat`; the MSIX itself is a ZIP-compatible OPC package.
- The manifest first lets Scoop extract the outer ZIP, then uses Scoop's official `Expand-ZipArchive` in `pre_install` to unpack a temporary `.msix.zip` copy into `$dir\\app`. It validates `AppxManifest.xml`, x64 identity, the main executable, and the Watchdog before removing the MSIX, certificate, and vendor batch file. The Start Menu shortcut points directly to `app\\WinMacShell.exe`.
- NixanDeck runs unpackaged from the Scoop version directory; the manifest does not add a new signing certificate or register a new MSIX package. During migration from the former MSIX manifest, `pre_install` removes only the current user's prior NixanDeck package registration. The old machine TrustedPeople certificate is intentionally left untouched.
- The app's `%APPDATA%\\WinMacShell` settings directory is junctioned to Scoop `persist`, including migration of existing settings when safe. Uninstall removes the owned junction and the app's own HKCU Run value while preserving persisted settings. The app's Watchdog PID file under LocalAppData is cleaned only when it is stale.
- Windows Actions [run 44756459760](https://github.com/kiro5678/kirobucket/actions/runs/44756459760) passed the migration test: it registered the previous MSIX package, ran the manifest's actual extraction and migration hooks, launched `WinMacShell.exe` for 15 seconds without `Add-AppxPackage`, verified the app wrote `config.json` into Scoop persist and registered its unpackaged startup fallback, confirmed Watchdog exit, and verified post-uninstall cleanup while retaining settings.
- This validates package extraction, direct process startup, basic settings persistence, startup fallback, and cleanup on a disposable Windows runner. It does not prove full interactive UI behavior or that Package Identity-dependent features such as StartupTask and UserNotificationListener work unpackaged; the upstream app has a WPN database notification fallback.

## Classification rules for future manifest changes

1. Inspect the actual downloaded asset and its archive contents. The `.exe`, `.msi`, or `.msix` extension alone does not determine the class.
2. If the manifest uses `installer` to run the vendor setup, classify it as Nonportable unless the setup is explicitly being used only as a file extractor or the vendor's documented portable mode is selected.
3. An MSI with no deprecated `msi` install block is normally treated as an archive by Scoop. An explicit `msiexec /i` command is a real installation and is Nonportable.
4. `#/dl.7z` tells Scoop to save the downloaded asset with an archive filename and extract it. It does not prove that the resulting files are a working portable application; inspect the extracted payload and launch target.
5. `innosetup: true` selects Inno Setup extraction. It does not mean that the vendor installation routine ran.
6. A normal installer that writes its files to `$dir` is still Nonportable if the manifest executes the vendor installation routine or installs/registers required system-level components such as services, drivers, AppX/MSIX packages, or fonts. User-level settings and registry entries created by the application itself when launched (for example, an HKCU startup entry) do not by themselves make the manifest Nonportable.
7. A Portable manifest may have data outside the Scoop directory. Record that as a data/persistence note, not as a reason to mark the manifest Nonportable.
8. A single-file executable that extracts required native DLLs or runtime binaries into `%LOCALAPPDATA%`, `%TEMP%`, or other Windows paths outside Scoop is Nonportable, even when the manifest does not run vendor setup. Distinguish these executable components from user settings, cache, and logs, which may remain outside Scoop under rule 7.
9. Reclassify a manifest whenever its URL, installer arguments, extraction method, or install hooks change. Update this document in the same commit.
